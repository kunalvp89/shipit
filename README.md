# ShipIt v5.0.0

**ZIP → GitHub repository → Vercel project → direct production deployment → live URL**

ShipIt is a mobile-first deployment gateway for projects generated by coding agents. Upload a ZIP from your phone and ShipIt creates the GitHub repository, pushes the code, creates the Vercel project, uploads the same project files directly to Vercel, starts a production deployment, waits for the result, and returns the live URL.

## v5.0 changes

- Fixes the v4.1 `repo_not_found` problem.
- Vercel no longer needs access to the GitHub repository for the initial deployment.
- GitHub authentication is used only for GitHub operations.
- Vercel authentication is used only for Vercel operations.
- Creates/gets the Vercel project without attaching a GitHub repository.
- Uploads each project file directly to Vercel using the Vercel file upload API.
- Creates a production deployment from those uploaded files.
- Waits for `READY`, `ERROR`, or `CANCELED` (up to 3 minutes).
- Returns the live production URL.
- Reuses an existing Vercel project with the requested project name.
- Keeps the ZIP safety checks and wrapper-folder detection.
- Uses `SHIPIT_VERCEL_TOKEN` instead of `VERCEL_TOKEN` to avoid collision with Vercel's own system environment namespace.

Vercel's current documentation explicitly supports REST API deployments by generating a digest for each file, uploading the files, and then creating a deployment that references them. citeturn4search2

## Environment

```env
GITHUB_TOKEN=github_pat_...
SHIPIT_VERCEL_TOKEN=vcp_...
```

Nothing else is required.

### GitHub token

The GitHub credential must be able to:

- read the authenticated user
- create private repositories
- create blobs, trees and commits
- update branches

### Vercel token

The Vercel access token must belong to an account/team that can:

- create projects
- create production deployments
- access the selected Vercel team/account

Vercel documents project creation through `POST /v11/projects` and REST API authentication using a bearer access token. citeturn4search0turn4search4

## Deployment flow

```text
Phone
  ↓
ShipIt
  ↓
Create GitHub repository
  ↓
Push files + commit
  │
  ├───────────────────────────┐
  ↓                           ↓
GitHub source            Vercel API
                            ↓
                    Create Vercel project
                            ↓
                    Upload project files
                            ↓
                    Production deployment
                            ↓
                         READY
                            ↓
                       🌐 Live URL
```

The important difference from v4.1 is that the Vercel step is **not** a GitHub import. Vercel receives the project files directly. This avoids requiring Vercel's GitHub integration to have access to the newly created repository.

## Future GitHub pushes

This v5 deployment is intentionally a direct-file deployment. A later GitHub commit will **not automatically redeploy Vercel** unless the Vercel project is connected to GitHub.

For ShipIt's mobile workflow, the recommended future model is for ShipIt to perform both operations itself whenever the user uploads a new ZIP:

```text
new ZIP
  ↓
GitHub commit
  ↓
Vercel direct production deployment
```

This keeps the workflow fully automated without requiring a Vercel GitHub import step.

Vercel's REST API supports direct deployments specifically for workflows where Git integration is not required. citeturn4search2

## ZIP structure

If an AI coding agent produces:

```text
project.zip
└── project-folder/
    ├── package.json
    ├── src/
    └── ...
```

ShipIt moves the wrapper contents to the repository root when `package.json` is found there.

The following are excluded:

- `.env*`
- `.git`
- `node_modules`
- `.vercel`
- `.next`
- `dist`
- `build`
- common OS/log files

Limits:

- ZIP: 25 MB
- individual file: 5 MB
- files: 500

## Vercel project naming

The UI can accept names such as:

```text
CreditBillReminder
```

ShipIt normalizes the value to a Vercel-compatible project slug such as:

```text
creditbillreminder
```

## Run locally

```bash
npm install
cp .env.example .env
# edit .env and add your two tokens
npm start
```

Open:

```text
http://localhost:3000
```

## Security

Both tokens are server-side only. They are never sent to the browser, stored in local storage, included in the GitHub repository, or written into the uploaded project.
